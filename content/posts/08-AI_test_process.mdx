최근 사이드 프로젝트와 회사 업무에 LLM을 적극적으로 도입해보면서 가장 크게 부딪힌 벽은 "'어떻게 이 결과물을 확신할 수 있는가?'"였습니다.
기가 막히게 잘 작동하다가도, 어느 날 프롬프트 단어 하나 바꿨을 뿐인데 전혀 엉뚱한 대답을 내놓는 경우가 부지기수였기 때문이죠.

이런 고민을 하던 차에 OpenAI에서 제공하는 [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 문서를 읽게 되었고,
AI 개발 패러다임이 단순히 '연동'에서 **검증**으로 넘어가고 있음을 확실히 느꼈습니다.

## 1. 인트로: AI를 여전히 신뢰할 수 있을까?

전통적인 소프트웨어 엔지니어링에서는 입력(Input)이 같으면 출력(Output)도 항상 같습니다.
하지만 생성형 AI는 태생적으로 **비결정적**(nondeterministic) 입니다. 똑같은 프롬프트를 던져도 그때그때 확률에 따라 다른 결과물을 뱉어낸다는 점이 포인트입니다.

결국 이 비결정적인 요소를 통제하고 애플리케이션의 신뢰성을 보장하려면, 기존의 유닛 테스트와는 다른 결을 가진 **체계적인 평가(Evals) 시스템**이 필수적입니다. 느낌에 의존하는 "잘 작동하는 것 같네"식의 위임적 형태의 테스트는 결국 운영 환경에서 대참사를 불러올 수밖에 없습니다.

---

## 2. 평가 프로세스 설계 방법 (OpenAI 권장 5단계)

OpenAI 가이드에서는 막연한 AI 평가를 시스템화하기 위해 다음 5단계의 프로세스를 권장하고 있습니다. 단순한 원칙을 넘어, 실제 LLM 애플리케이션을 구축할 때 어떤 고민을 해야 하는지 명확한 가이드를 제시합니다.

### 1단계: 평가 목표 정의 (Define eval objective)
평가의 성공 기준을 가장 먼저, 그리고 아주 구체적으로 설정해야 합니다.
단순히 "AI가 대답을 잘해야 함" 같은 모호한 목표는 피해야 합니다. 예를 들어, 고객센터 챗봇을 만든다면 "사용자의 질문에 친절하게 답한다"가 아니라, **"사용자의 복잡한 질문 속에서도 우선적으로 '주문 취소', '환불 규정' 등의 핵심 의도를 정확히 분류해 낸다"**처럼 명확한 기준이 필요합니다. 문서 요약 기능이라면 "원본의 핵심 맥락을 잃지 않으면서 지정된 분량과 포맷(JSON 등)을 준수하는가"가 목표가 될 수 있습니다.

### 2단계: 데이터셋 수집 (Collect dataset)
가장 품이 많이 들지만, Evals의 품질을 좌우하는 핵심 단계입니다.
단일한 데이터 소스에 의존하기보다 다양한 데이터를 혼합하는 것을 권장합니다.
* **프로덕션/과거 데이터:** 실제 서비스 로그나 사용자 피드백(좋아요/싫어요) 데이터
* **전문가 큐레이션 데이터(Golden Dataset):** 도메인 전문가가 직접 작성한 완벽한 '정답 셋'
* **합성 데이터(Synthetic data):** OpenAI 문서에서는 `o3`나 `GPT-4.1` 같은 뛰어난 추론 모델을 활용해 **다양한 엣지 케이스와 적대적(Adversarial) 테스트 데이터를 자동으로 생성**하여 평가 풀을 넓히는 것을 적극 권장합니다.

### 3단계: 평가 지표 정의 (Define eval metrics)
수집된 데이터를 바탕으로 목표 달성 여부를 수치화할 지표를 정합니다.
BLEU나 ROUGE 같은 전통적인 텍스트 유사도 지표에만 얽매일 필요는 없습니다.
* **RAG(검색 증강 생성) 앱의 경우:** 제공된 문서에서 정답을 얼마나 잘 가져왔는지 측정하는 **Context recall(문맥 재현율)**과 답변에 엉뚱한 소리가 없는지 확인하는 **Context precision(문맥 정밀도)**를 지표로 삼을 수 있습니다.
* **G-Eval 방식 도입:** 모델의 창의적인 텍스트 생성 결과물은 전통적 지표로 채점하기 어렵습니다. 이럴 때는 LLM 자체를 평가자로 삼아 논리적 일관성이나 가이드라인 준수 여부를 1~5점 척도로 채점하도록 기준을 세울 수 있습니다.

### 4단계: 평가 실행 및 비교 (Run and compare evals)
준비된 데이터셋과 지표를 바탕으로 본격적인 테스트를 실행합니다.
OpenAI의 Evals API 등을 활용하여 평가를 돌려보고, 프롬프트를 수정하거나 다른 모델(예: o1 모델과 GPT-4o 모델) 간의 결과를 비교해 봅니다. 이 과정을 통해 개발자는 '감'이 아닌 '수치화된 데이터'를 바탕으로 모델의 성능을 객관적으로 개선해 나갈 수 있습니다.

### 5단계: 지속적인 평가 (Continuously evaluate)
평가는 런칭 전 한 번 하고 끝내는 일회성 작업이 아닙니다.
CI/CD 환경에 평가 파이프라인을 구축하여, 프롬프트나 코드가 단 한 줄이라도 변경될 때마다 평가가 자동으로 실행되도록(Continuous Evaluation) 해야 합니다. 또한, 서비스 운영 중 새롭게 발견되는 비결정적 오류나 환각(Hallucination) 현상들을 지속적으로 모니터링하고, 이를 다시 2단계의 '데이터셋'에 편입시켜 평가 시스템 자체를 지속적으로 성장시켜야 합니다.

### 3. 실무/사이드 프로젝트에 직접 도입해볼 만한 방식 🚀

OpenAI의 문서를 꼼꼼히 읽고 나니, 당장 진행 중인 B2B 식품 소싱 플랫폼이나 회사 업무에 AI 평가 체계를 TDD(테스트 주도 개발)처럼 도입해 볼 수 있겠다는 확신이 들었습니다. 막연한 프롬프트 엔지니어링을 넘어, 백엔드 시스템의 일부로서 AI를 검증하기 위해 아래와 같은 파이프라인을 구상해 보았습니다.

### 🎯 평가 목표 정의: 프롬프트를 넘어선 시스템적 '계약(Contract)'
AI가 생성하는 결과물은 단순한 텍스트가 아니라 서비스 로직의 일부가 되어야 합니다. 따라서 평가 목표를 단순 프롬프트 텍스트로 두지 않고, 클라이언트/백엔드와 AI 간의 엄격한 **'데이터 계약(Contract)'**으로 정의해야 합니다.

* **Schema 중심의 설계:** AI의 역할과 비즈니스 로직을 `Zod`(TypeScript)나 `Pydantic`(Python)을 활용해 명확한 JSON 스키마로 정의합니다.
* **구조적 강제성:** OpenAI API의 `response_format` 기능(Structured Outputs) 등을 활용하여 AI가 반드시 이 스키마에 맞춰 응답하도록 고정시킵니다. AI가 스키마 구조를 정확히 지켰는지, 누락된 필수 필드는 없는지를 파싱(Parsing)하는 것 자체가 1차적인 강력한 평가 지표가 됩니다.

### 🧪 평가 지표 정의: 단위/통합 테스트에 'LLM-as-a-Judge' 패턴 도입
기존의 `assertEquals`처럼 예상 결괏값과 정확히 일치하는지 비교하는 테스트 코드는 비결정적인 AI 결과물 앞에서는 무용지물입니다. 이를 해결하기 위해 통합/단위 테스트 단계에 **LLM-as-a-Judge(AI를 평가자로 활용)** 패턴을 도입합니다.

메인 작업을 수행하는 무거운 모델(예: o1, GPT-4o)의 결과물을, **빠르고 저렴한 모델(예: GPT-4o-mini, Gemini Flash)이 평가자(Judge)가 되어 채점**하게 만드는 방식입니다.

```typescript
// 예시: AI의 시장 분석 리포트 결과물이 가이드라인을 준수하는지 검증하는 Jest 테스트
test('AI 시장 분석 리포트가 기획 가이드라인(Rules)을 준수하는지 검증', async () => {
  // 1. 메인 AI 모델에 분석 요청
  const aiResponse = await generateMarketReport(mockFoodData); // B2B 식품 데이터

  // 2. 가벼운 평가용 AI(Judge)에게 채점 요청
  const evaluation = await evalModel.evaluate({
    content: aiResponse,
    criteria: `
      1. 도매가/소매가 데이터가 현실적인 원화 범위 내에 있는가?
      2. 3문장 이내의 격식 있는 톤("~보입니다", "~평가됩니다")을 유지했는가?
      3. 광고성 멘트가 전혀 포함되지 않았는가?
    `,
    format: "JSON_WITH_SCORE"
  });

  // 3. 평가 결과 검증 (80점 이상일 때만 CI 통과)
  console.log(`평가 사유: ${evaluation.reason}`);
  expect(evaluation.score).toBeGreaterThan(80);
});
```

### 🔄 지속적인 평가: CI/CD 연동으로 '프롬프트 회귀(Regression)' 원천 차단
AI 개발 시 가장 당황스러운 순간은 **"A 케이스의 답변을 개선하려고 프롬프트를 살짝 수정했더니, 잘 작동하던 B 케이스가 완전히 망가졌을 때"**입니다.
이를 막기 위해 Evals 파이프라인을 CI/CD에 필수적으로 연동해야 합니다.

- GitHub Actions 연동: 프롬프트나 비즈니스 로직을 수정하고 PR(Pull Request)을 올리면, 사전에 구축해둔 50~100개의 벤치마크 데이터셋(정상 케이스 + 엣지 케이스)으로 자동 테스트 스크립트가 돌아갑니다.

- Merge Lock 설정: 테스트가 완료되면 PR 댓글로 자동 채점표(Pass Rate: 92%)가 달리게 하고, **전체 통과율이 90% 미만이라면 코드 Merge 자체를 차단(Block)**합니다. 이로써 무심코 수정한 프롬프트가 프로덕션에 치명적인 장애를 일으키는 것을 막을 수 있습니다.

## 마치며
"문제를 정의하고 로직의 흐름을 설계하면, 코딩 자체는 AI가 가장 빠르게 해준다"는 것을 몸소 느끼는 요즘입니다. 하지만 그 결과물이 정말 믿을 수 있는지, 서비스 장애를 일으키지 않을지 보증하는 것은 결국 개발자의 몫입니다.

OpenAI의 문서가 말하고자 하는 바는 명확합니다. "AI를 도입했다면, 그에 걸맞은 수준의 테스트 체계(Evals)도 함께 설계하라."

앞으로의 개발은 프롬프트를 잘 깎는 것을 넘어, '어떤 데이터를 넣고 어떻게 검증할 것인가'를 시스템적으로 설계하는 능력이 가장 중요한 경쟁력이 될 것입니다. 당장 진행 중인 프로젝트에 작은 평가 코드 하나부터 도입해 봐야겠습니다.
