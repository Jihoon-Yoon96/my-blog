# 이전 내용 요약 (FoodInsight 뼈대 다지기) 🏗️
본격적인 내용에 앞서, 이전 포스팅에서 진행했던 초기 세팅 과정을 짧게 요약해 보겠습니다.

기술 스택: Nuxt 3 + Tailwind CSS를 활용해 빠르고 직관적인 개발 환경을 구성했습니다.

공공데이터 연동: 식품안전나라 OpenAPI를 연결하여, 전국 식품 제조사 및 품목 데이터를 실제로 불러오는 1차 검색 로직을 구현했습니다.

AI 리포트 기능: 검색된 데이터를 바탕으로 Google Gemini API를 호출해 시장 요약, 예상 가격 추이, 판매량 등을 추론하는 스마트한 AI 리포트 생성 기능을 완성했습니다.

이렇게 핵심 뼈대를 잡은 후, 이번에는 **'사용자가 진짜 쓰기 편한 서비스'**로 만들기 위한 대규모 UI/UX 업데이트를 진행했습니다.

# 신규 작업 내용: UX의 디테일을 잡다 ✨
### 🌙  다크모드 지원
가장 먼저 진행한 작업은 다크모드 적용입니다. 대시보드 화면은 정보량이 많아 눈이 쉽게 피로해질 수 있죠.
화면 우측 하단에 귀여운 플로팅 토글 버튼을 배치하고, Tailwind의 dark: 클래스를 활용해 컴포넌트 단위로 색상을 꼼꼼히 매핑했습니다. 라이트 모드의 화사한 느낌과 다크 모드의 깊은 네이비(bg-[#0F172A]) 톤이 부드러운 트랜지션과 함께 전환되도록 구현했습니다. (로컬 스토리지를 활용해 새로고침 시 테마 유지도 빼놓지 않았습니다!)

### ⚡ 제로 딜레이! 클라이언트 사이드 필터링
기존에는 카테고리나 정렬 기준이 바뀔 때마다 매번 서버를 통해 OpenAPI를 호출했습니다. 하지만 이 방식은 필연적으로 응답 지연을 발생시켰습니다.

그래서 검색 플로우를 과감하게 바꿨습니다!
사용자가 검색어를 입력하면, 서버에서는 최대 1,000건의 데이터를 한 번에 가져와 클라이언트로 넘깁니다. 그리고 화면에서는 받아온 데이터 내에 실제 존재하는 제품 유형만 추출해 동적인 체크박스 필터를 만들어냅니다. 사용자가 체크박스를 누르거나 정렬 버튼을 누르면 Vue의 computed가 즉각적으로 리스트를 필터링하고 페이징해 줍니다. 깜빡임 없는 제로 딜레이 필터링이 완성된 순간이었습니다.

### 📊 동적 대시보드
대시보드 화면이 정적이면 재미가 없죠. 사용자의 인터랙션에 따라 차트와 수치가 실시간으로 변하는 재미를 주고 싶었습니다.

경쟁사 분석 연동: '집중 경쟁업체'를 드롭다운에서 변경하면, 하단의 파이 차트(제품유형별 비중)와 라인 차트(신제품/매출 동향)의 데이터가 해당 경쟁사에 맞춰 즉시 재계산됩니다.

라인 차트 오버레이: 파란색 실선(자사 데이터)과 초록색 점선(경쟁사 데이터)을 SVG 레이어로 겹쳐 그리고, 꺾이는 꼭짓점마다 실제 수치 텍스트가 따라다니도록 구현했습니다.

### 📂 '저장된 리포트' 전용 페이지 분리
기존에 메인 화면 한편에 있던 저장된 리포트 영역을 떼어내어, 사이드바 메뉴를 통해 접근할 수 있는 단독 페이지(/reports)로 만들었습니다. 덕분에 대시보드 레이아웃의 통일성이 유지되고, 사용자가 과거에 분석했던 AI 리포트들을 훨씬 쾌적한 화면에서 열람할 수 있게 되었습니다.

# 마무리 (AI 잘 쓰고 싶다! 🤔)
이번 기능 고도화 작업을 진행하면서 코딩 자체보다도 **'AI 코딩 어시스턴트를 어떻게 하면 더 똑똑하게 쓸 수 있을까?'**에 대한 고민을 정말 많이 하게 되었습니다.

최근 LLM 생태계를 보면 RAG(검색 증강 생성), LangChain 기반의 체인 구성 등 AI를 효율적으로 활용하기 위한 방법론과 라이브러리들이 하루가 다르게 쏟아져 나오고 있습니다.

그런데 제 스스로의 작업 방식을 돌아보니, **"나는 무식하게 토큰만 엄청 낭비하면서 쓰고 있었구나"**라는 생각이 들었습니다.
예를 들어 특정 컴포넌트의 아주 작은 부분(버튼 하나, 변수 하나)만 수정하면 되는데도, "여기서 이거 고쳐줘!"라며 전체 프로젝트 파일과 수백 줄의 코드를 통째로 프롬프트에 때려 넣고 학습시켜 버리는 방식으로 질문을 하고 있었던 거죠.

이러한 방식은 AI가 문맥을 파악하기엔 쉬울지 몰라도, 불필요한 토큰 낭비가 심하고 오히려 답변의 정확도를 떨어뜨리거나 엉뚱한 곳을 건드리는 부작용을 낳기도 합니다.

이번 경험을 통해 최소한의 컨텍스트(토큰)만 주입하여 최대한의 정확도와 효율을 뽑아내는 '프롬프트 엔지니어링' 연습이 개발자에게 필수적인 역량이 되었다는 것을 뼈저리게 느꼈습니다.

앞으로는 프로젝트의 덩치가 더 커질 텐데, 전체 코드를 냅다 던지는 방식에서 벗어나 질문의 범위를 좁히고 필요한 모듈만 떼어서 질문하는 **'토큰 다이어트'**를 적극적으로 실천해 보려고 합니다.
