# 시작 계기
항해 수료 후 꿀같은 휴식을 즐기고 있던 중, 항해 기간 동안 치열하게 움직였던 습관이 아직 남아 있었는지 문득 “이렇게 쉬어도 되나…?” 하는 생각이 들었다.

그러던 와중에 마침 ‘블로그 제작 스터디’ 모집 글을 보게 되었고, 3주 안에 간단히 배포까지만 하면 된다는 안내를 보고 “부담 없이 공부해보기 딱 좋겠다!” 싶어 참여하게 되었다.

또 개발 중에 검색을 하다 보면 많은 프론트엔드 개발자들이 직접 만든 블로그에서 글을 정리하고 있는 모습을 자주 보게 되는데, 그 모습이 참 멋있어 보였고 포트폴리오용으로도 좋겠다는 생각을 늘 해왔던 터라 이번 기회를 살려 나만의 블로그를 직접 만들어보기로 했다.

# 계획 세우기 - 1. CMS도입? MDX사용?


가장 먼저 고민했던 부분은 **“블로그 글을 어떻게 관리할 것인가?”**였다.
DB 없이 프론트엔드만으로 구성할 예정이었기 때문에, 글 관리 방식은 크게 두 가지 선택지로 나뉘었다.

1. 외부 플랫폼을 CMS로 활용하기 (예: Notion, Obsidian 등)
2. 소스 레벨에서 직접 관리하기 (MDX 활용)

먼저 1번 방식은 글 관리가 매우 편리하다는 점이 가장 큰 장점이다.
다만 Notion의 경우 마크다운이 아닌 블록(Block) 기반 구조로 제공되기 때문에, 이를 파싱하기 위한 추가 로직이 필요하고 이미지 링크 만료 처리 등도 직접 고려해야 했다. 이로 인해 예상 개발 기간이 다소 길어질 것 같다는 부담이 있었다.

반면, 2번 방식은 1번에 비해 글 관리 측면에서는 다소 불편할 수 있지만, 블로그 구축 자체만 놓고 보면 훨씬 간단한 구조였다.
또한 MDX 기반 블로그는 이미 많은 개발자들이 사용하고 있어 제작 후기나 참고 자료가 풍부하다는 점도 큰 장점으로 느껴졌다.

결국

> “3주 안에 결과물을 만들어보자!”
“실제로 사용해보고 너무 불편하면 그때 CMS를 도입하자!”

라는 기준을 세우고, 이번 프로젝트에서는 MDX로 글을 관리하는 구조를 채택하기로 했다.

# 계획 세우기 - 2. 검색 기능을 넣고싶어!

글을 얼마나 자주 쓰게 될지는 아직 모르지만, 블로그 역시 게시판의 한 형태라고 생각했기 때문에 검색 기능은 꼭 필요하다고 느꼈다.
문제는 DB 없이 프론트엔드만으로 구현해야 한다는 점이었다. 처음엔 막막했지만, 여러 자료를 찾아본 결과 `fuse.js`와 `velite`를 함께 사용하면 클라이언트 단에서도 충분히 쓸 만한 검색 기능을 구현할 수 있겠다는 결론에 이르렀다.

### 1. fuse.js - 검색 기능 구현
`fuse.js`는 클라이언트와 Node 환경 모두에서 사용할 수 있는 퍼지 검색(Fuzzy Search) 라이브러리다.
퍼지 검색이란 정확히 일치하는 문자열뿐만 아니라, 유사한 문자열까지 찾아주는 검색 방식을 의미한다.

백엔드 검색 엔진을 따로 구축하기에는 과하고, 단순한 `.filter()` 기반 검색만으로는 아쉬운 상황에서 `fuse.js`는 꽤 적절한 선택지로 보였다.
특히,

- 별도의 의존성이 없고
- 비교적 가볍게 동작하며
- 검색 대상 key별로 가중치를 설정할 수 있다는 점

덕분에 DB 없이 검색 기능을 구현하기에 알맞은 라이브러리라고 판단했다.

다만, 검색 라이브러리가 있다고 해서 바로 검색을 할 수 있는 것은 아니었다.
검색 대상이 될 데이터 자체를 어떻게 관리할 것인가라는 또 다른 문제가 남아 있었다.

### 2. velite - 검색을 위한 데이터 관리
처음에는 블로그 글(MDX 파일)을 작성할 때마다 검색용 JSON 데이터를 따로 관리해야 하나 고민했다.
하지만 글의 생성·수정·삭제마다 검색 데이터를 수동으로 관리하는 방식은 너무 번거롭고 실수할 여지도 많아 보였다.
결국, 파일 변경에 따라 검색용 데이터가 자동으로 갱신되는 구조가 필요하다고 느꼈다.

그 과정에서 알게 된 라이브러리가 바로 `velite`였다.

`Velite`는 Markdown, MDX, YAML, JSON과 같은 정적 파일들을
TypeScript로 타이핑된 데이터로 변환해 주는 콘텐츠 관리 라이브러리다.
파일 시스템에 있는 컨텐츠를 마치 DB에서 데이터를 꺼내 쓰는 것처럼,
안전하고 일관된 형태로 사용할 수 있게 도와주는 도구라고 이해했다.

이를 활용하면:

- MDX 파일을 기반으로 깔끔한 JSON 데이터 리스트를 생성하고
- 해당 데이터를 fuse.js에 넘겨
- 클라이언트 단에서도 동작하는 검색 기능을 구현할 수 있다

는 그림이 그려졌다.

결과적으로, `velite` + `fuse.js` 조합이
DB 없이 블로그 검색 기능을 구현하기 위한 현실적이고 깔끔한 선택이라고 판단했다.

# 계획 세우기 - 3. 댓글은 있어야 하지 않을까?

블로그를 게시판의 여러 형태 중 하나라고 생각하다 보니, 댓글 기능도 빠질 수 없겠다는 생각이 들었다.
하지만 이 역시 DB 없이 구현해야 했기 때문에 처음에는 막막했다. 그러던 중 다른 분들의 프로젝트 계획이나 회고 글을 읽다 보니, `giscus`를 활용해 댓글 기능을 도입했다는 사례를 접하게 되었다.

조금 더 찾아보니, `giscus`는 GitHub의 Discussions 기능을 기반으로 웹사이트나 블로그에 댓글 시스템을 연동해 주는 오픈 소스 라이브러리였다.
쉽게 말해, 블로그 글 하단에 작성된 댓글들이 내 GitHub 저장소의 Discussions 탭에 하나의 스레드로 차곡차곡 저장되는 구조다.
별도의 DB 없이도 댓글 기능을 구현할 수 있다는 점이 인상적이었다.

게다가 완전 무료로 사용할 수 있고, 광고나 트래킹도 없으며 UI 또한 깔끔해 보여 블로그에 부담 없이 적용하기에 딱 적합하다고 느꼈다.

결국 댓글 기능은 Giscus를 활용하는 방향으로 결정하게 되었다.

# 최종 계획
위 세 가지 계획들과 나머지 짜잘한 것들을 정리하면서 아래와 같은 계획이 탄생했다.


**기술 스택**
- **코어:** Next.js + TS
- **스타일:** Tailwind + shadcn
- **상태관리:** Zustand
- **콘텐츠관리:** Velite (MDX → JSON 데이터로 정리), Giscus (댓글)
- **검색:** Fuse.js (클라이언트 단에서 검색 - Velite로 만들어진 JSON 활용)
- **배포:** Vercel

** 세부 내용 **
1. **레이아웃 (Layout)**
- **GNB(공통):** 홈 이동, 검색, 프로필 사진
- **LNB(목록 화면만):** 시리즈(폴더) 토글 목록 (반응형)
- **공통모달팝업:** 일단은 검색용어로만.. (나중에 다른 모달 쓸 수 있으니..)

2. **목록**
- **UI:** 반응형 카드 배치 (PC 3열 / Tab 2열 / Mob 1열)
- **기능:** 날짜순 정렬, 시리즈 필터링

3. **상세**
- **UI:** 타이틀 / 내용 / 댓글 (좀 더 고민 필요..)
- **기능:** 댓글 등록 (Giscus)

4. **검색**
- **UI:** 전역 모달 팝업 (shadcn Command 컴포넌트)
- **기능:** 제목 검색, 태그 검색

5. **데이터**
- **Velite:** 빌드 단계에서 mdx파일의 메타데이터를 JSON으로 자동 변환
