# 0. 모달 관리 구조

프로젝트 초기에는 각 페이지마다 필요한 모달 컴포넌트를 일일이 import 해서 사용하는 방식이었다. 하지만 서비스 규모가 커지며 모달의 종류가 늘어나자 모달 레아웃 및 호출 등에서 중복 코드가 발생하고 신규 모달 UI를 생성할때마다 번거로운 작업이 반복됐다.

이를 해결하기 위해 레이아웃 레벨에서 모달을 호출하는 방식으로 변경하게 됐다. 모든 페이지가 공유하는 최상위 레이아웃(layouts.vue)에 일종의 모달 슬롯(Dynamic Component)을 하나 배치해두고, **어떤 모달을 렌더링할지(type)**와 **언제 보여줄지(status)**를 Vuex 전역 상태로 원격 제어하는 방식인 것이다. 덕분에 개별 페이지에서는 UI에 대한 고민 없이 비즈니스 로직에만 집중할 수 있는 구조로 잘 리팩토링한 것 같다.

### UI 구조
- layouts.vue 파일에서 공통 모달 레이어 배치
- modals.js의 state값(소스 상으로 modalType) 기준으로 동적 컴포넌트 호출 구조
(` <component is="..." /> `)

# 1. 문제 인식 (요구사항의 변화)
초기 모달 시스템은 매우 단순했다. state에 status(boolean)와 type(string)을 두어, 한 번에 하나의 모달만 띄우고 닫는 구조였다.

하지만 서비스가 고도화되면서 두 가지 핵심적인 요구사항이 발생했고, 기존 구조로는 이를 수용하기 어려워졌다.

### 요구사항 1: 모달 간 데이터 전달과 순차 실행
"A 모달에서 값을 입력하고 확인을 누르면, A가 닫히면서 B 모달이 열리고, A에서 입력한 값이 B에 반영되어야 한다."

--> 기존에는 모달이 닫히는 시점과 데이터가 처리되는 시점이 분리되어 있어, 모달의 결과값을 다음 로직으로 매끄럽게 넘겨주기 어려움

### 요구사항 2: 다중 모달창 구현
"A 모달이 열려있는 상태에서, 그 위에 B 모달(예: 로딩, 상세 설정 등)을 띄워야 한다."

--> 기존 state는 단일 객체였기에(item), 새로운 모달을 열면(commit) 기존 모달의 상태가 덮어씌워져 사라지는 문제가 있음

# 2. 고민 과정
이 문제를 해결하기 위해 데이터 흐름의 제어와 상태 구조의 변경이라는 두 가지 측면에서 고민을 거듭했다.

### 1) 비동기 데이터 전달을 위한 Promise 도입
가장 먼저 떠올린 방법은 기존 state에 데이터를 전달받을 params 객체를 추가하는 것이었다.
```javascript
export const state = () => ({
  status: false,
  type: 'defaultModal',
  item: {},
  params: {} // A모달 -> B모달로 넘길 데이터를 저장할 공간
})
```
하지만 이 방식은 곧바로 한계에 부딪혔다. 모달이 열리고 닫힐 때마다 **"어떤 시점에 params를 읽고, 언제 초기화해야 하는가?"**에 대한 명확한 기준을 세우기 어려웠기 때문이다. 상태 관리가 복잡해질수록 데이터가 오염되거나, 엉뚱한 모달에 이전 데이터가 남아있는 사이드 이펙트가 우려되었다.

이때 문득 **"모달을 여는 행위 자체를 비동기 함수로 취급하면 어떨까?"**라는 생각이 스쳤다.

보통 우리는 비동기의 대상을 '서버 API 응답'이나 '파일 로딩' 등으로 한정 짓곤 한다. 하지만 관점을 조금만 바꿔보면, "사용자가 화면을 보고 내용을 확인한 뒤 버튼을 누를 때까지 기다리는 시간" 또한 훌륭한 비동기 작업이다.

개발자 입장에서 사용자가 1초 뒤에 확인 버튼을 누를지, 10초 뒤에 누를지 알 수 없다는 점은, 서버가 언제 응답을 줄지 알 수 없는 상황과 본질적으로 동일하다.

### Promise의 생명주기와 메모리 관리
이 아이디어를 확신으로 바꾸기 위해, 자바스크립트 Promise의 내부 동작, 특히 메모리 관리 메커니즘을 다시 깊게 파고들어 보았다.

MDN 문서 등에 따르면 Promise는 생성 직후부터 종료될 때까지 Pending, Fulfilled(Resolved), Rejected 중 하나의 상태를 가진다. 여기서 주목한 것은 Pending 상태일 때의 메모리 동작이었다.

- **Pending 상태 (대기)** : Promise 객체가 생성되고 resolve나 reject가 호출되지 않은 상태라면, 자바스크립트 엔진은 이 객체와 연결된 핸들러들을 힙 메모리에 계속 유지한다. 비동기 작업이 언제 끝날지 모르기 때문에 가비지 컬렉터가 이를 회수하지 않고 기다린다.
- **Settled 상태 (완료)** : 상태가 결정(Resolve/Reject)되면, 비로소 후속 처리 메서드들이 마이크로태스크 큐로 넘어가 실행되고, 참조가 사라지면 가비지 컬렉터에 의해 메모리에서 해제된다.

**"resolve를 호출해주지 않으면 Promise는 영원히 Pending 상태로 메모리에 살아있다."**
이 원리는 모달 시스템을 설계하는 데 결정적인 힌트가 되었다. 우리가 인위적으로 resolve 함수를 쥐고 있다가, 사용자가 버튼을 누르는 순간 호출해 준다면 완벽한 동기화가 가능해지는 것이다.


나는 앞서 분석한 Promise의 메커니즘을 모달 UI의 생명주기에 대입하여 설계를 구체화해보았다.

- **pending** : 모달 열림 (await modalOpen() 호출 시점 -> 사용자의 입력을 기다리며 코드 실행이 일시 정지됨)
- **Resolve** : 확인 버튼 클릭 (사용자가 행동을 완료함-> resolve가 실행되며 입력받은 데이터를 반환하고 모달이 닫힘)
- **Reject** : 취소/닫기 (사용자가 취소함 -> 흐름을 종료하거나 에러 핸들링으로 분기)

이렇게 설계하면 모달을 호출하는 쪽에서는 복잡한 콜백이나 상태 감시(watch) 없이, await 키워드 하나만으로 **"모달이 열리고 -> 사용자가 입력하고 -> 닫힐 때까지"**의 흐름을 직관적인 순차 코드로 작성할 수 있게 된다.

### 2) 다중 모달을 위한 리팩토링 (Object -> Array)
요구사항 2(다중 모달 요구사항)이 나왔을 때, 단일 객체로는 물리적으로 불가능했다. 사실 객체 구조를를 쪼개면 가능이야 하겠다만... 그럼 기존에 모달을 호출하는 페이지들의 로직들을 하나하나 다 반영하면서 수정해줘야 하지 않나? 라고 생각하게 됐다.

내가 내린 결론은 화면에 쌓이는 모달의 특성을 고려했을 때 모달 상태 state의 타입을 배열로 바꾸는 것이 가장 적합했다. (신규 상태값으로 modals: [])
```javascript
export const state = () => ({
  status: false,
  type: 'defaultModal',
  modals: [], // 신규 모달 관리 state
  item: {},
  cancel: {}
})
```

- 열기: 배열에 모달 객체를 push
- 닫기: 배열의 마지막 요소를 pop (혹은 특정 인덱스 splice)
- 전체 닫기: 배열 초기화

이 과정에서 앞서 고민했던 Promise 패턴을 이 배열 구조에도 동일하게 적용하여, "여러 개의 모달이 쌓이더라도 각각 비동기적으로 결과값을 반환" 할 수 있도록 고도화했다.

# 3. 최종 결과물
이런 고민의 과정을 거쳐서 아래의 결과물을 도출해낼 수 있었다.

```javascript
// modal.js

export const state = () => ({
  /** 삭제 항목들 **/
  // status: false,
  // type: 'defaultModal',
  // item: {},
  modals: [],
  cancel: {}
})

export const mutations = {
  MODALS_CLOSE (state, key) {
    if (state.cancel) {
      try {
        state.cancel()
      } catch (e) {}
    }
    // loading 모달창 닫기
    state.modals.forEach((modal, index) => {
      if (modal.type === 'loading') {
        state.modals.splice((index, 1))
      }
    })
    state.modals.pop()
  },
  MODALS_OPEN (state, payload) {
    let obj = payload
    // 기존 modals의 key값 동일하면 다시 랜덤 수 배정
    state.modals.push(obj)
  },
  MODALS_ALL_CLOSE (state) {
    state.modals = []
  },
  ...
}

export const actions = {
  modalsOpen ({ commit, state, dispatch }, item) {
    return new Promise(resolve => {
      item.key = Math.floor(Math.random(1, 100) * 1000)
      item.close = function (result) {
        resolve(result)
        dispatch('modalsClose')
      }
      commit('MODALS_OPEN', item)
    })
  },
  modalsClose ({ commit }, key) {
    commit('MODALS_CLOSE', key)
  },
  modalsAllClose ({ commit }) {
    commit('MODALS_ALL_CLOSE')
  }
  ...
}

```
